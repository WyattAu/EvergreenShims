# ADR-008: expect() with Descriptive Messages over unwrap()

## Status: Accepted

## Date: 2026-06-07

## Context

A v1.0.1 audit identified 47 `unwrap()` calls in production library code. While `unwrap()` is acceptable in tests and examples, in production code it produces unhelpful panic messages (e.g., "called Result::unwrap() on an Err value") that make debugging difficult in production environments where shims run as PID 1.

## Decision

Replace all `unwrap()` calls in library crates with either:

1. `expect("descriptive message")` — for invariant assumptions that should never fail (e.g., `config.tenants.iter().enumerate()` where the vec was just validated).
2. `?` operator or explicit match — for fallible operations that can reasonably fail at runtime.

The `expect()` message must explain *what* was expected and *why* the failure is considered a bug. Example:

```rust
// Before (unhelpful panic message)
let addr: SocketAddr = config.health.listen.parse().unwrap();

// After (descriptive)
let addr: SocketAddr = config.health.listen.parse()
    .expect("health.listen is validated as a SocketAddr before startup");
```

## Consequences

- **Positive**: Production panics now include actionable diagnostic messages; debugging time reduced; no functional behavior change.
- **Negative**: Slightly more verbose code; developers must write meaningful messages; `expect()` still panics (vs returning `Result`).

## Alternatives Considered

1. **Replace all unwrap() with Result**: Not always possible (e.g., in `Default::impl` or static initialization); adds boilerplate without safety benefit for true invariants.
2. **Use `assert!()` macros**: Produces different panic output; doesn't integrate with `std::panic::set_hook` for structured logging.
3. **Use `cfg_attr(debug_assertions, ...)`**: Doesn't help in release builds where production debugging matters most.
