# ADR-009: #[cfg(test)] Modules for Integration Test Helpers

## Status: Accepted

## Date: 2026-06-07

## Context

Several shims need test helper functions (mock servers, temporary directories, config builders) that are only used in `#[cfg(test)]` or integration tests. Placing these in the public API would pollute the crate's surface area and force downstream users to see test-only types. Placing them in a separate `tests/` directory loses access to private internals.

## Decision

Use `#[cfg(test)]` modules within source files to house test helpers that need access to private internals. For helpers that don't need private access, prefer the `tests/` directory for integration tests.

Pattern:

```rust
#[cfg(test)]
mod test_helpers {
    pub fn mock_config() -> Config {
        // builds a valid Config for testing
    }
}
```

This keeps test infrastructure co-located with the code it tests while ensuring it is excluded from release builds via conditional compilation.

## Consequences

- **Positive**: Test helpers have access to private fields and constructors; zero runtime cost (`#[cfg(test)]` is compile-time gated); helpers are discoverable near the code they test.
- **Negative**: Test helpers compiled separately for each crate's test suite (no sharing across crates); large helper modules can clutter source files.

## Alternatives Considered

1. **Separate `test-utils` crate**: Adds a workspace dependency; requires making internals public or using `pub(crate)` with `#[doc(hidden)]`.
2. **`dev-dependencies` with re-exports**: Works for public APIs but doesn't help with private internals.
3. **Feature-gated test helpers**: Adds a compile-time feature flag complexity; risk of accidentally including test helpers in release builds.
4. **`tests/` directory only**: Loses access to private internals; forces making types public for testing.
