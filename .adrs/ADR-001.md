# ADR-001: PID 1 Execution Model

## Status: Accepted

## Date: 2026-06-07

## Context

EvergreenShims runs as the primary process inside minimal scratch/musl containers. The shim must act as PID 1, responsible for process lifecycle, signal forwarding, zombie reaping, and graceful shutdown. Standard init systems (tini, dumb-init) add binary dependencies and image size; Rust can handle these responsibilities natively.

## Decision

Each shim binary runs as PID 1 using a Rust-native init loop. The process:

1. Installs `SIGTERM` and `SIGHUP` handlers via `nix::sys::signal`.
2. Spawns the child work process (the actual application or database driver).
3. Forwards signals to the child process group.
4. Waits for child exit with a configurable timeout (`shutdown_timeout_secs`).
5. Reaps zombie processes via `waitpid` with `WNOHANG`.

## Consequences

- **Positive**: Zero external init dependencies; smaller Docker images (~2.5 MB); full control over shutdown semantics; SIGHUP triggers config hot-reload.
- **Negative**: Must correctly implement POSIX process lifecycle; subtle bugs in signal handling or zombie reaping can cause container hangs; requires thorough integration testing.

## Alternatives Considered

1. **tini init**: Adds ~20 KB binary, well-tested, but introduces an external dependency and an extra layer of process indirection.
2. **dumb-init**: Similar to tini, written in C, requires musl cross-compilation.
3. **Go-based init**: Heavier runtime, larger binary, unnecessary complexity for a Rust project.
4. **Kubernetes sidecar pattern**: Defers init to the orchestrator, but breaks the self-managing container model.
