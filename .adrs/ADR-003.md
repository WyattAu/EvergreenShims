# ADR-003: Capability Trait as Core Abstraction

## Status: Accepted

## Date: 2026-06-07

## Context

EvergreenShims composes multiple shims (health, vault, backup, migration, etc.) into a single binary. Each shim provides distinct capabilities (health checking, secret rotation, backup scheduling). The system needs a uniform way to discover, initialize, and invoke these capabilities at runtime without tight coupling between shims.

## Decision

Define a `Capability` async trait in `shim-core` that every shim implements. The trait provides:

- `name()` — unique identifier for the capability.
- `start()` — initialize and begin background work.
- `stop()` — graceful shutdown.
- `status()` — current health/state of the capability.

The `ShimBus` broadcasts lifecycle events to all registered capabilities, enabling cross-shim coordination without direct dependencies.

## Consequences

- **Positive**: New shims are added by implementing one trait and registering with the bus; testability via mock capabilities; clear separation of concerns.
- **Negative**: Trait object dispatch adds minimal runtime overhead; all capabilities share the same lifecycle semantics (start/stop/status) which may not fit every edge case.

## Alternatives Considered

1. **Enum-based dispatch**: Simpler but requires modifying the enum for every new shim, violating open/closed principle.
2. **Function pointers**: No shared state or lifecycle management, harder to test.
3. **Plugin system (dynamic loading)**: Adds complexity of shared library loading, symbol resolution, and ABI stability concerns.
4. **Macro-based registration**: Reduces boilerplate but obscures the trait interface.
