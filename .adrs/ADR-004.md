# ADR-004: ShimBus In-Process Broadcast

## Status: Accepted

## Date: 2026-06-07

## Context

Multiple shims within a single binary need to communicate lifecycle events (config reload, health state changes, backup triggers) without direct coupling. An external message broker (Redis, NATS) would add operational complexity and network dependencies that contradict the single-binary deployment model.

## Decision

Implement an in-process broadcast channel (`ShimBus`) using `tokio::sync::broadcast`. The bus:

1. Publishes typed events (`ConfigReloaded`, `BackupTriggered`, `HealthChanged`, etc.).
2. Allows any capability to subscribe to events by type.
3. Uses `parking_lot::RwLock` for shared configuration state.
4. Supports filtered subscriptions via `subscribe_filtered()` for event-specific handling.

## Consequences

- **Positive**: Zero network overhead; all communication is in-memory; backpressure via broadcast channel capacity; typed events prevent serialization bugs.
- **Negative**: Limited to single-process communication (not suitable for multi-instance coordination); broadcast channel has a fixed capacity and will drop old messages if subscribers are slow.

## Alternatives Considered

1. **Redis pub/sub**: Adds network dependency, serialization overhead, and operational complexity; suitable for cross-instance communication but overkill for intra-process events.
2. **Crossbeam channels**: Synchronous only, would block the async runtime.
3. **Flume**: MPSC channel, doesn't support broadcast pattern.
4. **Direct function calls**: Creates tight coupling between shims; makes testing difficult.
