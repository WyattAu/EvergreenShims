# ADR-007: ring-free aws-lc-rs for musl Compatibility

## Status: Accepted

## Date: 2026-06-07

## Context

EvergreenShims targets static musl builds (`x86_64-unknown-linux-musl`, `aarch64-unknown-linux-musl`, `riscv64gc-unknown-linux-musl`) for scratch-based Docker images. The `ring` crate requires a C compiler and assembly toolchain that frequently breaks musl cross-compilation, causing CI failures and developer friction.

## Decision

Replace `ring` with `aws-lc-rs` as the default crypto provider across the workspace:

- `reqwest` uses `rustls-tls-no-provider` (no default TLS provider) with `rustls` configured to use `aws-lc-rs`.
- `sqlx` uses `tls-rustls-aws-lc-rs` feature.
- `rustls` uses the `aws-lc-rs` feature instead of the `ring` feature.
- `rcgen` and `acme-micro` operate on PEM/DER directly and are provider-agnostic.

This is documented in workspace `Cargo.toml` comments and enforced by `cargo-deny` advisory checks.

## Consequences

- **Positive**: musl cross-compilation works without `cmake`, `clang`, or assembly toolchain; Docker builds are reproducible; `aws-lc-rs` is FIPS-capable.
- **Negative**: `aws-lc-rs` has a larger build-time dependency footprint (C/C++ compiler required at build time, but not at link time); slightly longer CI build times (~15s) for the C compilation step.

## Alternatives Considered

1. **Stick with ring**: Known to break musl builds; requires `cmake` and `clang` in CI; frequently causes cross-compilation failures on ARM/RISC-V.
2. **Use `rustls` with `ring` backend**: Same problem as ring directly.
3. **Use `native-tls`**: Depends on OpenSSL, which adds a large C dependency and is harder to cross-compile for musl.
4. **Use `boring`**: TLS library from Google; less mature Rust bindings and ecosystem support.
